# miTch Landing Page Structure

## Page Goal

Convert a skeptical visitor into a demo request by making one thing obvious:
miTch proves only what is needed, and keeps the rest withheld.

## Information Hierarchy

1. What miTch is
2. Why it matters
3. How it works
4. Proof that it is real
5. What to do next

## Section 1: Hero

### Headline

Prove only what is needed.

### Subcopy

miTch is the privacy firewall for identity proofs. Verifiers get the minimum answer they need. Raw data stays out.

### Primary CTA

See the live demo

### Secondary CTA

Request a pilot

### Visual direction

Show a wallet control surface with three visible states:

- requested
- allowed
- withheld

## Section 2: Problem

### Headline

Identity checks should not become data leaks.

### Subcopy

Most systems still ask for too much. That creates retention risk, compliance overhead, and unnecessary trust loss.

### Support points

- KYC and verification flows often collect more than the verifier needs
- central storage turns identity into an exposure problem
- privacy promises do not help once raw data has already moved

## Section 3: Solution

### Headline

Built to mediate proofs, not store identities.

### Subcopy

miTch sits between the wallet and the verifier. It evaluates policy, reduces disclosure to the minimum, and records the decision.

### Support points

- selective disclosure by design
- fail-closed policy
- auditable decision trail
- no blind trust in the verifier request

## Section 4: How It Works

### Headline

One request in. One minimal proof out.

### Steps

1. Verifier requests a claim
2. miTch checks policy locally
3. Wallet reveals only the allowed claim
4. Audit trail records the event
5. Unused data stays withheld

### Microcopy

No raw identity dump. No persistent over-sharing. No silent allow.

## Section 5: Use Cases

### Headline

Where selective disclosure matters most.

### Cards

- Age verification
- Healthcare access
- Professional eligibility
- Public-sector authorization

### Card rule

Each card should say what the verifier gets, not what the user loses.

## Section 6: Proof

### Headline

This is not a concept. It is a working system.

### Subcopy

Show implementation proof, not only claims.

### Proof blocks

- live demo
- test coverage
- policy engine
- audit transparency

## Section 7: Trust

### Headline

Privacy should feel controlled, memorable, and manageable.

### Subcopy

The user should understand what is shared, why it is shared, and what stays hidden.

### Support points

- explicit consent flow
- visible disclosure boundary
- clear audit outcome
- fail-closed handling of ambiguity

## Section 8: Audience Split

### Enterprise

Reduce exposure, retention risk, and privacy overhead.

### Product teams

Ship proof flows without building a data hoarding layer.

### Public sector

Support regulated checks without centralizing unnecessary identity data.

## Section 9: FAQ

### Headline

Questions buyers will ask.

### Suggested questions

- Is miTch a wallet?
- Does miTch store identity data?
- What happens when policy is unclear?
- How does auditability work?

### Answer style

Short, concrete, no abstract security theater.

## Section 10: Final CTA

### Headline

Make the next identity flow smaller.

### Subcopy

Use miTch when the verifier needs a proof, not a copy.

### CTA

Request a pilot
