# ADR-011: Two-Tier Audit Model — Minimised, Accountable, Tamper-Evident

**Date:** 2026-06-06
**Status:** Accepted
**Deciders:** Jonas (Late-bloomer420)

---

## Context

A "clean" audit for AskMI must satisfy two legal pulls that point in opposite
directions:

1. **Data minimisation & unlinkability** — GDPR Art. 5(1)(c), Art. 25
   (data protection by design/default), eIDAS 2 (Reg. (EU) 2024/1183,
   Art. 5a), and the EUDI Wallet core-functionality implementing regulation
   (Reg. (EU) 2024/2979, Art. 8 transaction logs) require the wallet to give
   the user transparency without letting the wallet provider / issuer track the
   user across verifiers.
2. **Sectoral retention & accountability** — GDPR Art. 30 (Records of
   Processing Activities), Art. 32 (integrity/security), plus sector law
   (AML/GwG, JuSchG age proof, EHDS Reg. (EU) 2025/327 access logging, AO/HGB
   tax retention) require *retained, attributable* evidence.

A single audit store cannot serve both. We must avoid both failure modes:
logging too much (minimisation breach) and logging too little to be
accountable (Art. 30/32 breach).

This ADR fixes the **structure** of the audit. It deliberately does **not**
fix jurisdiction-specific *parameters* (retention periods, which sectors
require attributable logs) — those differ across the 27 member-state
transpositions and require qualified DPO/legal sign-off. The structure below
is member-state-agnostic; the parameters are configuration.

## Decision

Adopt a **two-tier model with an optional sector overlay**:

### Tier 1 — User-facing transaction log (eIDAS 2 Art. 5a; Reg. 2024/2979 Art. 8; GDPR Art. 15/17)
- Lives **on-device** in the wallet, full detail **for the data subject only**.
- Powers the user dashboard, the "report an unlawful request" duty, subject
  access (Art. 15), and erasure (Art. 17, crypto-shredding).
- Not a minimisation problem: the user views their *own* data.
- Implemented by the wallet receipt history (`consent-manager/receipt-store`),
  not by this schema.

### Tier 2 — External audit export (GDPR Art. 30 + 32 accountability)
- The artefact handed to auditors / supervisory authorities / the controller.
- **PII-free**: salted, rotated `verifierHash`; 5-minute `timestampBucket`;
  no stable cross-RP correlators (consistent with ADR-005).
- **Accountable**: every record carries its lawful basis (Art. 6(1)), purpose
  code (Art. 5(1)(b)), data categories touched as claim *names* only
  (Art. 5(1)(c) evidence), the authorising `policyHash`, and a `retentionUntil`
  (Art. 5(1)(e)).
- **Tamper-evident**: records form a hash chain (`prevRecordHash` →
  `recordHash`), so deletion/insertion/reordering is detectable (Art. 32).
- Implemented by `@askmi/policy-engine` → `audit-export-schema.ts` (this ADR
  extends it from schema 1.0 → 1.1).

### Sector overlay (only where the law compels attributable retention)
- A **separate**, access-controlled store with its own lawful basis
  (Art. 6(1)(c) legal obligation) and its own statutory retention period.
- **Never** mixed into the Tier-2 minimised export.
- Out of scope for this ADR beyond the requirement that it be kept separate.

## Schema 1.1 — required accountability fields (Tier 2)

Added to `AuditExportRecord` (all **required** — an audit record without these
is not Art. 30-capable):

| Field | Legal anchor | Notes |
|-------|--------------|-------|
| `legalBasis` | GDPR Art. 6(1)(a)–(f) | enum: consent / contract / legal_obligation / vital_interests / public_task / legitimate_interests |
| `purposeCode` | Art. 5(1)(b) purpose limitation | code, never free-text PII |
| `dataCategories` | Art. 5(1)(c) minimisation | claim **names** only (token pattern enforced), never values |
| `policyHash` | Accountability / reproducibility | which authorised policy decided this |
| `retentionUntil` | Art. 5(1)(e) storage limitation | ISO-8601; when this record expires |
| `prevRecordHash` / `recordHash` | Art. 32 integrity | hash chain; genesis prev = 64 zeros |

Bundle (`AuditExportBundle`) 1.1 adds `controller` (Art. 30 controller
identity + RoPA reference) and `chainTipHash` (last `recordHash`).

## Consequences

**Positive:** Tier-2 export is simultaneously minimised *and* accountable;
tamper-evidence is cryptographic, not procedural; 7-year escrow retention
(`escrow-backup.ts`, `retentionDays: 2555`) stays defensible precisely because
the export is PII-free; structure is jurisdiction-agnostic.

**Negative:** Producers of audit records must now supply lawful basis / purpose
/ policy hash at decision time (no retrofitting). Hash-chaining requires ordered
append. Jurisdiction parameters still need DPO sign-off — this ADR does not and
cannot assert 27-state compliance, only a compliant structure.
