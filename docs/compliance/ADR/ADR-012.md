# ADR-012: Audit Anchor Backend — Transparency Log (RFC 9162) as default, L2 contract optional, no own chain

**Date:** 2026-11-20
**Status:** Proposed (owner decision pending — tracks #295 / L2A-03)
**Deciders:** Jonas (Late-bloomer420)

---

## Context

The audit log (`src/packages/audit-log`) anchors batches of decision hashes to an
external backend so that tampering with the local log is detectable later. Today no
real anchoring exists: `StateAnchorClient` (`src/packages/audit-log/src/anchor.ts`)
returns `network: 'mock'`, `status: 'mocked'` receipts (honest since #301 / `21fc573`,
after #297 / `850818e`). The remaining work is #294 (real submit + verify, L2A-02),
which depends on this backend decision (#295 / L2A-03).

Existing building blocks:

- `src/packages/anchor-service` defines the `AnchorProvider` interface
  (`publishRoot(root, meta) -> AnchorRef`) with two **stub** providers:
  `EthereumL2AnchorProvider` (Polygon/Arbitrum/Optimism contract call) and
  `TransparencyLogAnchorProvider` (RFC 9162 / Rekor-style log). Both are marked
  STUB — no real RPC/HTTP calls yet.
- `L2AnchorClient` (`src/packages/audit-log/src/storage/l2-anchor-client.ts`) has
  networks `optimism-mainnet|optimism-sepolia|arbitrum-one|arbitrum-sepolia|mock`
  and `verifyAnchorDetailed()` returning `verified | mock | pending | unverifiable`.
  No path reaches `verified` yet.

Constraints:

1. **No own chain** (L2A-03): running our own validator/L2 is out of scope.
2. **Privacy / unlinkability** (ADR-011): only Merkle **roots** of decision hashes
   may leave the device — never raw events, DIDs or claim values. A root is a
   random-looking hash, but batch timing/size can still leak usage volume, so batch
   windows and sizes stay configurable (`AnchorServiceConfig.maxBatchWindowMs`,
   `maxBatchSize`).
3. **Fail-closed verification** (ADR-008): an unverifiable receipt must never read
   as success; `verified` is only reachable through a real, signature-checked proof.
4. **No always-on signing key on the wallet** if avoidable: key custody is the
   hardest operational problem. A backend that needs no wallet-held key is preferred
   for the default path.

## Options

| Option | Submit | Verify | Key needed | Public visibility | Cost | Notes |
|---|---|---|---|---|---|---|
| A. RFC 9162 transparency log (Rekor-compatible) | append entry, get inclusion promise | inclusion proof + signed tree head vs log public key | none for submit (log signs) | root hash is public | free/cheap | append-only, CT-style auditability; log availability is the trust anchor |
| B. L2 contract (Optimism/Arbitrum) | contract call `anchor(root, batchId, count)` | on-chain event + Merkle proof | signer key + gas (or EIP-4337) | root public on-chain | gas per batch | strongest ordering/finality; key custody + cost; stub exists |
| C. RFC 3161 TSA | timestamp request per root | verify TSA signature on token | none for submit (TSA signs) | token holds the root hash | per-timestamp fee | simple, but per-root cost and TSA trust; no batching benefit |

## Decision (proposed)

**Default: Option A — RFC 9162 transparency log.** Submit = append root to a
Rekor-compatible log; verify = inclusion proof + signed tree head checked against the
log's pinned public key. No wallet-held signing key, append-only audit trail, cheap
enough for batch cadence. The existing `TransparencyLogAnchorProvider` stub is the
port target.

**Optional: Option B — L2 contract** for deployments that need on-chain finality
(e.g. sectoral retention demanding public-chain evidence). Kept as a second
`AnchorProvider`; requires an operator-held signer key and gas budget, configured
per deployment, never in the wallet.

**Rejected as default: Option C — TSA per root**, because per-root fees and the lack
of batching make the batch model pointless; keep RFC 3161 only as an offline fallback
format if a deployment has no log access.

## Consequences

- Port `L2AnchorClient` onto the `AnchorProvider` interface from
  `@askmi/anchor-service` (reconcile the two: one interface, one receipt type
  `L2AnchorReceipt`/`AnchorRef`), so audit-log stops owning network specifics.
- Receipts must carry the verification material (log entry UUID / signed tree head,
  or tx hash + block) so `verifyAnchorDetailed()` can reach `verified` fail-closed.
- Privacy: anchor only `merkleRoot(batch)`; keep `maxBatchWindowMs`/`maxBatchSize`
  config; document that public roots still reveal batch timing (volume metadata).
- `network` labels stay honest: `'mock'` for the fallback until a real provider is
  configured; never `confirmed` without a verified proof.
- Follows #294 (L2A-02) implementation and its dated `docs/qa/` evidence.
